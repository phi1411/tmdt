# SÀN THƯƠNG MẠI ĐIỆN TỬ ĐA NGÀNH HÀNG — E-COMMERCE

Database chính bắt buộc:
- MongoDB Document Store

Đây là đồ án học thuật nhưng sản phẩm cuối phải có trải nghiệm gần giống một website thương mại điện tử thực tế.

QUAN TRỌNG:

Trong PHASE này CHƯA code feature nghiệp vụ.

Mục tiêu hiện tại là:
1. Phân tích requirement.
2. Thiết kế kiến trúc tổng thể.
3. Thiết kế cách tổ chức repository.
4. Tạo hệ thống tài liệu để các AI coding agent ở những session sau không phải đọc toàn bộ repository.

==================================================
I. YÊU CẦU BẮT BUỘC CỦA ĐỀ TÀI
==================================================

Barem:

1. BÁO CÁO & THIẾT KẾ CSDL — 2.5 điểm

Phải chứng minh:

- MongoDB phù hợp với sản phẩm đa ngành có thuộc tính không cố định.
- Product sử dụng Polymorphic Schema.
- Order sử dụng Embedded Documents.
- Có giải thích rõ khi nào embed và khi nào reference.

2. CRUD NỀN TẢNG — 2.5 điểm

Phải có:

- CRUD Category.
- CRUD Product.
- Tạo Order.
- API backend.
- Giao diện quản lý.

3. CHỨC NĂNG NÂNG CAO — 2.5 điểm

Order bắt buộc phải snapshot thông tin sản phẩm tại thời điểm mua.

Ví dụ order item:

{
  productId,
  sku,
  productName,
  image,
  priceAtPurchase,
  quantity,
  selectedAttributes,
  lineTotal
}

Không được thiết kế kiểu chỉ lưu productId rồi sau này truy vấn Product để lấy giá hiện tại.

Nếu:

giá khi mua = 10.000.000

sau đó Admin thay thành:

12.000.000

thì Order cũ vẫn phải giữ:

priceAtPurchase = 10.000.000

Aggregation Pipeline bắt buộc phải thể hiện:

- $match
- $unwind
- $group
- $sort

Phải có ít nhất:

- Doanh thu theo thời gian.
- Top 5 sản phẩm bán chạy.

4. KIỂM THỬ & DEMO — 2.5 điểm

Dummy Data yêu cầu tối thiểu:

Products:
- >= 100 documents.
- >= 3 ngành hàng.

Orders:
- 50–100 documents.
- mỗi Order có 2–5 Product embedded.

Phải demo trực tiếp trên MongoDB Compass và Web.

IV. PRODUCT POLYMORPHIC SCHEMA
==================================================

Tất cả sản phẩm đa ngành phải nằm chung:

products

KHÔNG tạo:

products_electronics
products_fashion
products_home
...

Product có phần field chung và attributes linh hoạt.

Ví dụ:

{
  "_id": ObjectId,
  "sku": String,
  "name": String,
  "slug": String,
  "categoryId": ObjectId,
  "brand": String,
  "description": String,
  "price": Number,
  "stock": Number,
  "images": [String],
  "attributes": Object,
  "status": String,
  "createdAt": Date,
  "updatedAt": Date
}

Ví dụ Electronics:

attributes:
{
  "ram": "8GB",
  "storage": "256GB",
  "chip": "...",
  "screen": "...",
  "battery": "..."
}

Fashion:

attributes:
{
  "sizes": ["S", "M", "L"],
  "colors": ["Black", "White"],

V. ORDER & EMBEDDED DOCUMENT
==================================================

Order là một aggregate rất quan trọng.

Order phải embed snapshot của sản phẩm.

Ví dụ:

{
  "_id": ObjectId,

  "orderCode": String,

  "userId": ObjectId,

  "customerSnapshot": {
    "name": String,
    "phone": String,
    "email": String
  },

  "shippingAddress": {
    "receiverName": String,
    "phone": String,
    "addressLine": String,
    "ward": String,
    "district": String,
    "province": String
  },

  "items": [
    {
      "productId": ObjectId,
      "sku": String,
      "productName": String,
      "image": String,
      "priceAtPurchase": Number,
      "quantity": Number,

      "selectedAttributes": {
        ...
      },

      "lineTotal": Number
    }
  ],

  "subtotal": Number,
  "shippingFee": Number,
  "discount": Number,
  "total": Number,

  "paymentMethod": String,
  "paymentStatus": String,
  "orderStatus": String,

  "createdAt": Date,
  "updatedAt": Date
}

Order history phải độc lập với các thay đổi sau này trong Product.

==================================================
VI. CART
==================================================

Cart phải có business rule rõ ràng.

Backend là source of truth.

Frontend không được tự quyết định giá cuối cùng.

Khi Add To Cart hoặc Checkout:

Backend phải kiểm tra:

- Product tồn tại.
- Product đang ACTIVE.
- quantity >= 1.
- quantity không vượt stock.
- Giá phải lấy lại từ Product hiện tại.
- Không tin price được gửi từ frontend.

Quyết định Cart nên:

- embed trong User

hoặc:

- collection carts riêng

phải được phân tích và ghi vào architecture/database docs.

Không tự chọn mà không giải thích trade-off.

XV. CHANGE POLICY
==================================================

Không được:

- tự đổi database architecture
- tự đổi collection
- tự đổi API contract
- tự đổi naming convention
- refactor module không liên quan
- thêm dependency tùy tiện
- thêm role tùy tiện
- thay MongoDB bằng database khác
- biến Document Database thành thiết kế SQL giả dạng MongoDB

Nếu cần thay đổi kiến trúc lớn:

1. Giải thích vấn đề.
2. Đưa phương án.
3. Nêu trade-off.
4. Ghi decision document.
5. Sau đó mới thực hiện khi requirement cho phép.

==================================================
XVI. TESTING & DEFINITION OF DONE
==================================================

Feature chỉ DONE khi:

- code chạy được
- API hoạt động
- validation đúng
- authorization đúng
- không có lỗi runtime
- test liên quan pass
- edge cases quan trọng đã kiểm tra
- docs được cập nhật nếu behavior thay đổi

Không báo DONE nếu test đang fail.
